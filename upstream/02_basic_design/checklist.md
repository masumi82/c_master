# 基本設計書のレビュー観点

レビューする人（Claude を含む）はこの一覧を基準に見る。各項目には雛形の章番号を付けてある。

## 方針と構成（1〜2章）
- [ ] 設計方針の各行が要件 ID を引いているか。要件にない条件で設計を決めていたら、その条件は要件定義書に戻す
- [ ] ハードウェア構成図にケーブル種別と距離があるか。PC 線とセンサ線のそれぞれに、距離に対する対策が書かれているか
- [ ] 部品一覧の概算の合計が、要件の予算に収まっているか。収まらないなら未決事項に載っているか
- [ ] ソフトウェア構成に、コマンド解釈・測定・判定・記録・ランプ制御が現れているか。1つのモジュールが全部やっていないか

## 機能一覧（3章）
- [ ] 要件定義書の機能要件がすべて表にあるか（抜けを探す）
- [ ] 表にあるが要件にない機能はないか。あるなら要件定義書に追加するか、削る

## 外部インターフェース（4章）
- [ ] PC との通信に、速度・データ長・パリティ・ストップビット・行終端がそろっているか
- [ ] コマンド仕様が `cmd_dispatch` で扱える形式か（1行、空白区切り、先頭がコマンド名）
- [ ] コマンドごとに正常応答と異常応答があるか。異常応答の形式が1つに統一されているか
- [ ] 各コマンドが `cmd_dispatch` の制約（コマンド名を含めて8トークンまで、空白1文字区切り、応答は1回1バッファ）に収まっているか。応答が長くなるコマンド（記録の一覧）の返し方が決まっているか
- [ ] 設定値を読むコマンドと書くコマンドの両方があるか（書けるが読めない設定は保守できない）
- [ ] 現場の人がパソコンを使わない、という要件と矛盾する操作をコマンドに要求していないか
- [ ] センサ故障の検出方法が書かれているか。「値が返ってこない」と「ありえない値が返る」の両方

## 状態遷移（5章）
- [ ] 停電復帰後の状態が図にあり、要件定義書で決めたとおりになっているか
- [ ] すべての状態から抜ける遷移があるか（入ったら出られない状態がないか）
- [ ] 状態ごとのランプの表があり、正常と異常と停電後の3つが見分けられるか

## データ（6章）
- [ ] 設定値の範囲と初期値があるか。初期値は顧客の議事録の数字か
- [ ] 記録の保持件数が「先週の夜が見られる」要件から計算されているか（間隔 × 日数）
- [ ] 記録が満杯になったときの扱いが書かれているか

## 異常処理（7章）
- [ ] 表の各行に、検出方法と振る舞いと見せ方の3つがそろっているか
- [ ] 異常処理の結果として、装置が「知らせない」状態に落ちる経路がないか（監視装置が黙るのは最悪の故障）

## 非機能（8章）
- [ ] 要件定義書の非機能要件がすべて表にあり、確認方法が書かれているか

## 文書全体
- [ ] 要件定義書に書くべきこと（顧客の目的、業務の背景）が混ざっていないか
- [ ] 詳細設計に送るべきこと（関数名、変数名、ソースの構成）が混ざっていないか。コマンド名は基本設計、関数名は詳細設計
- [ ] Mermaid の図が3つ以上あるか（構成、ソフトウェア、状態遷移）
