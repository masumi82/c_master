# upstream（上流工程の練習・別件・2〜3日）

要件定義書と基本設計書を、組込み機器を題材に自分で書き、レビューを受ける練習です。C の1週間とは独立していますが、題材の UART コマンド仕様は `phase1_lang/ex04_cmd_table` の振り分け方式で実装できる形にするので、ex04 の README を先に読んでおくと設計が具体的になります。

## V字モデルでの位置づけ
```
要件定義 ──────────────── 受入テスト
   基本設計 ──────────── 結合テスト
      詳細設計 ──────── 単体テスト
            実装
```
左側の各工程で「何を決めたか」が、右側の同じ高さのテストで「確認する項目」になります。3日目に作るトレーサビリティ表は、この左右の対応を1枚にしたものです。詳細設計と見積もりは今回の範囲外です。

## 3日間の予定

| 日 | やること | 成果物（自分で書く） | 目安 |
|---|---|---|---|
| 1日目 | `00_theme/依頼メモ.md` を読み、Claude を顧客役にしてヒアリング。`01_requirements/template.md` に沿って要件定義書を書く | `01_requirements/ヒアリング議事録.md`、`01_requirements/要件定義書.md` | 3〜4h |
| 2日目 | `02_basic_design/template.md` に沿って基本設計書を書く。図は Mermaid | `02_basic_design/基本設計書.md` | 3〜4h |
| 3日目 | `03_traceability/template.md` でトレーサビリティ表を作る。レビューを受けて3つの文書を直す | `03_traceability/トレーサビリティ表.md` | 2〜3h |

## Claude の使い方

### 顧客役（1日目）
「`upstream/00_theme/顧客.md` の顧客として答えてください。議事録は `upstream/01_requirements/ヒアリング議事録.md` です」と伝えてから質問します。Claude は顧客.md と議事録（あれば）を読んでから答えるので、日をまたいでも回答が食い違いません。答えは自分で議事録に書きます。顧客は技術者ではないので、ボーレートやセンサの型番を聞いても「わからない、そちらで決めてほしい」と返ってくることがあります。そのときは「こちらで決めて要件に書き、確認してもらう」のが仕事です。

`顧客.md` の後半「学習者は読まないこと」の節は、質問で引き出すための答えです。見ないのは自己申告です。各日の `checklist.md` は書く前に読んでかまいません（答えは書いてありません）。

### レビュー（各日の終わり、3日目）
「`upstream/01_requirements/要件定義書.md` をレビューして」のように依頼します。レビューを頼まれた Claude は、同じディレクトリの `checklist.md` を基準に、SIer の部門長視点と QA 視点の2つで見ること（この2視点は個人設定の `review-sier` / `review-qa` サブエージェントで実現しているので、別の環境では依頼時に「2つの視点で」と添えてください）。

## ルール
- 雛形（`template.md`）の目次は一般的な SIer の構成です。会社の標準様式があるなら、そちらに合わせて雛形を書き換えてかまいません
- 要件には `REQ-F-001` のような ID を振ります。3日目のトレーサビリティ表はこの ID をたどるので、途中で振り直さないでください
- 「未決事項」は空欄にせず、決められなかったことをそのまま書きます。全部決まった要件定義書は、ふつう何かを隠しています
- 模範解答の要件定義書はリポジトリに置きません
